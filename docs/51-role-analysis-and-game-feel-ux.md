# Role Analysis and Game Feel UX

## Purpose

Soro-pon lets users create decks, tiles, categories, roles, and scoring rules.

Because user-created decks can grow in unexpected directions, the role analysis engine and UX must not depend on a specific starter deck, fixed role list, or a guessed player intent.

This document fixes the design principles for:

- role analysis
- wait analysis
- wildcard assignment
- candidate ranking
- hand sorting
- role preview UX
- effect timing
- explainability
- deck validation

The goal is to keep the game understandable, flexible, and pleasant even when roles increase or wildcard-heavy custom decks appear.

## 1. Core Principle

The game must not decide what the user is trying to do.

Instead, the engine always analyzes all meaningful candidates and returns ranked options.

The UI must not say:

```text
You are aiming for this role.
```

The UI should say:

```text
Close candidate
Can win now
High score candidate
One tile away
This tile would complete this candidate
```

## 2. Mahjong Reference Principle

Mahjong does not know the player's intent.

It checks completed hands, waits, and scoring patterns by evaluation, not by intent guessing.

Soro-pon follows the same principle:

```text
Do not infer the player's intent.
Analyze every candidate.
Rank candidates by transparent rules.
Explain why each candidate is valid, close, blocked, or invalid.
```

## 3. Hand Order Is Not Rule State

Hand order must not affect role evaluation.

Hand sorting is a UX feature, not a rule feature.

Fixed:

```text
Manual hand order: allowed
Automatic hand sorting: allowed
Role evaluation from hand order: forbidden
```

The player can freely rearrange tiles.

The system can suggest better arrangements, but it must not silently change the player's hand order during candidate preview.

## 4. Hand Sorting Modes

MVP should support or reserve structure for these sorting modes:

```text
recommended: sort by the highest ranked role candidate
category: group by category/tag/name/color-like deck metadata
acquired: keep draw/acquisition order
manual: user-defined order
```

Recommended sorting should be generated by `HandSorter` from `HandAnalyzer` results.

## 5. Candidate Preview

Selecting, tapping, or hovering a role candidate should temporarily preview how the hand relates to that candidate.

Preview may:

- brighten tiles used by the candidate
- dim unrelated tiles
- show ghost slots for missing requirements
- show wildcard assignment marks
- show wait labels
- show blocked reasons

Preview must not permanently reorder the hand.

Only an explicit action such as `Sort by this candidate` may change the hand order.

## 6. Candidate Classes

`HandAnalyzer` should classify candidates into these classes.

```ts
type RoleCandidateState =
  | 'completed'
  | 'tenpai'
  | 'near'
  | 'bonusOnly'
  | 'invalidButExplainable';
```

### completed

A `win_role` is already complete.

This candidate can become a tsumo/ron candidate if the surrounding action rules allow it.

### tenpai

The candidate is one tile away.

The UI should show the concrete wait.

### near

The candidate is more than one tile away but close enough to be useful.

MVP constant:

```text
near = two tiles away by default
```

### bonusOnly

A `special_bonus` or `ScoreBonus` is satisfied or close, but it cannot win by itself.

The UI must clearly say that it is bonus-only.

### invalidButExplainable

A candidate is structurally close but blocked by rules.

Examples:

- requires too many wildcards
- special_bonus only
- ScoreBonus only
- discarded wildcard ron is blocked
- required tile count does not fit the current variant

## 7. Candidate Ranking

The UI should show at most three primary candidates during normal play.

Ranking priority:

1. can win now
2. one tile away
3. two tiles away
4. higher score
5. fewer wildcards used
6. more natural tile matches
7. stronger bonus synergy
8. shorter and clearer explanation

High score must not always win over clarity.

For beginner-friendly UX, completion distance is more important than maximum theoretical score.

## 8. Wildcard Policy

Wildcards may exist in multiple copies.

MVP standard rule:

```text
A hand may contain multiple wildcards.
A single win_role may use at most one wildcard by default.
A single set/group may use at most one wildcard by default.
Discarded wildcard ron is blocked by default.
Wildcard assignment is automatic by default.
```

The system should not force the user to manually choose wildcard assignment every turn.

## 9. Wildcard Resolver

`WildcardResolver` must evaluate possible wildcard assignments as candidate data.

It should return enough information for UI and scoring.

```ts
type WildcardResolution = {
  usedWildcardCount: number;
  assignments: WildcardAssignment[];
  naturalMatchCount: number;
  blockedReason?: WildcardBlockedReason;
};
```

Examples of blocked reasons:

```text
requiresTooManyWildcards
maxWildcardsPerRoleExceeded
maxWildcardsPerSetExceeded
discardedWildcardRonBlocked
wildcardNotAllowedForRole
wildcardNotAllowedForScoreBonus
```

## 10. Wildcard UI

When a wildcard is used in a candidate, UI must show the temporary assignment.

Examples:

```text
★ as Bird
★ as Red category
★ as Moon tag
```

This assignment is candidate-specific.

The same wildcard may appear in different assignments across different candidate previews.

The UI must not imply that a wildcard has been permanently converted unless the final win/scoring result is being shown.

## 11. Ron / Tsumo Candidate Rule

Only `Role.kind = 'win_role'` can become a ron/tsumo candidate.

Fixed:

```text
win_role: can win
special_bonus: after-win bonus only
ScoreBonus[]: after-win score bonus only
```

Forbidden:

```text
special_bonus-only ron
special_bonus-only tsumo
ScoreBonus-only win
ScoreBonus as ron candidate
```

## 12. Wait Analysis

Wait display must be concrete.

Bad:

```text
One tile away
```

Good:

```text
One tile away: Bird category
One tile away: Red category
One tile away: tile with Moon tag
One tile away: any tile completing the third set
```

If many individual tiles satisfy the wait, prefer category/tag/condition labels instead of listing every tile.

## 13. Explain Engine

Every candidate should include a machine-readable explanation payload.

The UI can turn that payload into short text.

Required explanation examples:

```text
3 of 3 sets complete
2 of 3 sets complete
Needs one Bird category tile
Needs one Red category tile
This role would require 2 wildcards, but the limit is 1
Discarded wildcard cannot be used for ron
special_bonus is complete, but it cannot win by itself
ScoreBonus is complete, but it cannot win by itself
This role is not available in the normal variant
```

The player should be able to understand why an action is available or unavailable without reading a rulebook.

## 14. Effect Policy

Normal play should remain quiet.

Effects should explain state, not decorate everything.

### Normal candidates

Use soft paper-edge emphasis, not heavy glow.

### completed candidate

A completed set or role can have a subtle lantern edge.

### tenpai candidate

Show a faint ghost slot or missing-tile marker.

### wildcard assignment

Use a small ink/star mark on the wildcard tile.

### ron available

Use a clear lantern glow around the action and related tiles.

### tsumo available

Emphasize the drawn tile first, then the completed candidate.

### win result

Use paper layering, ink spread, and small lantern pulse.

Do not use generic explosions, constant particles, or full-screen noisy effects in normal play.

## 15. Always Visible Match Clarity

During match UI, the player should be able to understand:

- whose turn it is
- whether they can discard
- whether ron is available
- whether tsumo is available
- what the closest candidates are
- what the current waits are
- whether wildcard assignment is involved
- why a tempting candidate is blocked

Compact mode may reduce decoration and logs, but must not remove the minimum clarity for hand, discard, turn, win/pass actions, and top candidates.

## 16. Engine Responsibilities

### RoleMatcher

Evaluates whether one role condition is satisfied.

### WildcardResolver

Enumerates and evaluates wildcard assignment candidates.

### HandAnalyzer

Analyzes the whole hand and produces completed/tenpai/near/bonusOnly/invalidButExplainable candidates.

### WaitAnalyzer

Computes missing conditions and wait labels.

### IntentRanker

Ranks candidates without claiming player intent.

### ExplainEngine

Produces structured reasons for completion, waits, blocks, and invalid candidates.

### HandSorter

Suggests hand orders for readability.

### ScoreCalculator

Calculates score from `win_role`, `special_bonus`, and `ScoreBonus[]` without mixing their responsibilities.

## 17. Deck Validation

Deck validation must prevent custom decks from becoming unplayable or confusing.

### Errors

Errors block match start.

Examples:

```text
no win_role exists
role has no condition
win_role has zero or negative score
role requires an impossible tile count for the selected variant
normal variant contains only extended-size roles
special_bonus-only deck
ScoreBonus-only deck
```

### Warnings

Warnings allow play but should be shown to the deck creator.

Examples:

```text
role is too dependent on wildcards
same or near-identical role condition exists multiple times
role name is too long for match UI
very high score for a very easy role
role explanation is missing
candidate display may be noisy because too many similar roles exist
```

## 18. UI Wording

Avoid intent claims.

Bad:

```text
You are aiming for Animal Trio.
```

Good:

```text
Close candidate: Animal Trio
Can win: Animal Trio
One tile away: Bird category
This tile completes Animal Trio
```

## 19. MVP Required Implementation Targets

When engine implementation starts, the following structures should exist before full match UI:

```text
HandAnalyzer
WildcardResolver
WaitAnalyzer
IntentRanker
ExplainEngine
HandSorter
candidate state types
candidate ranking tests
wildcard assignment tests
cannot-win bonus-only tests
wait explanation tests
```

## 20. MVP Non-goals

Do not build these in MVP Phase 1:

```text
AI intent prediction
manual wildcard assignment every turn
large advanced analysis overlay
always-on heavy effects
full strategy advisor
online meta optimization
```

## 21. Final Rule

Soro-pon should not be a game that decides for the player.

It should be a game that makes the player's options easy to understand.

The engine analyzes all candidates.
The UI shows the most useful candidates.
The player still chooses how to play.
