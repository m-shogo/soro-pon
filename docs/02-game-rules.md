# Game Rules

## Rule Lock

`soro-pon` の対局ルールは、最終的に **ドンジャラと同じルール** として作る。

ここでいう「同じ」とは、雰囲気だけではない。  
以下の対局構造を変えない。

- 3〜4人で遊ぶ
- 共通の山を使う
- 各プレイヤーが手牌を持つ
- 自分の番で1枚引く
- あがらない場合は1枚捨てる
- 役を満たす組み合わせであがる
- あがり手は3枚セット×3組、合計9枚を基本形にする
- 役ごとの得点を合計またはルールに従って計算する
- 役と得点はデッキごとに定義できる

AIエージェントは、勝手に別ゲーム化しないこと。

禁止:

- 麻雀の複雑な符計算へ寄せる
- カードバトル化する
- 2人用ゲームとして作る
- 手札枚数やあがり形を独自に変える
- 「ライト化」と称してあがり構造を変える
- ユーザー定義役を軽視する

## Public Wording

開発資料では「ドンジャラと同じルール」と明記する。  
ただし、公開用LP・アプリ内説明・SNS公式文言では、既存商品名や既存IPに依存した表現を使わない。

公開向けの説明例:

```text
絵柄牌をそろえて役を作る、3〜4人用のカスタム牌ゲーム。
```

## Players

- 3人戦
- 4人戦
- 2人戦は作らない
- MVPは人間1人 + CPU2〜3人
- 全員が同じ山・同じ役表を使う

## Deck / RuleSet

このゲームにおける「デッキ」は、カードゲームの個人デッキではなく、その卓で使うルールセットを意味する。

```text
Deck = Tiles + Roles + Scoring Rules
```

デッキに含めるもの:

- 牌一覧
- 牌ごとの枚数
- カテゴリ定義
- 役一覧
- 役ごとの条件
- 役ごとの得点
- 3人戦/4人戦対応設定

## Tile / Hand Structure

基本構造:

- 通常時の手牌は8枚
- 自分の番で1枚引き、手牌は一時的に9枚になる
- 9枚であがり判定を行う
- あがらない場合は1枚捨て、手牌は8枚に戻る
- あがり形は3枚セット×3組、合計9枚

この構造をUI・状態設計・テストの前提にする。

## Turn Loop

基本ループ。

1. 現在プレイヤーが山から1枚引く
2. 手牌が9枚になる
3. 9枚であがれるか判定する
4. あがる場合は結果へ進む
5. あがらない場合は1枚捨てる
6. 他プレイヤーが捨て牌であがれるか判定する
7. 誰もあがらない場合、次のプレイヤーへターンが移る

MVPで段階実装する場合でも、最終ルール構造はこの形から変えない。

## Win Shape

あがり手は、基本的に3枚セット×3組。

```text
[set A: 3枚] + [set B: 3枚] + [set C: 3枚] = 9枚
```

各セットがどの役に該当するか、または9枚全体でどの役に該当するかは、デッキのRole定義で決める。

## Roles and Scoring

このゲームのキーは、ユーザーが役と得点を決められること。

Role は以下を持つ。

- id
- name
- points
- condition
- description optional

得点は固定ではなく、デッキごとに定義する。

## MVP Role Conditions

最初に対応する役条件。

### contains_all

指定した牌IDをすべて含む。

```json
{
  "type": "contains_all",
  "tileIds": ["tile_a", "tile_b", "tile_c"]
}
```

### same_name_count

同じ名前の牌が指定枚数ある。

```json
{
  "type": "same_name_count",
  "name": "きつね",
  "count": 3
}
```

### same_category_count

特定カテゴリを持つ牌が指定枚数ある。

```json
{
  "type": "same_category_count",
  "category": "森",
  "count": 3
}
```

### all_different_categories

指定枚数の牌がすべて異なるカテゴリ条件を満たす。

```json
{
  "type": "all_different_categories",
  "count": 3
}
```

### exact_group

指定した牌セットが完全に揃う。

```json
{
  "type": "exact_group",
  "tileIds": ["tile_a", "tile_b", "tile_c"]
}
```

## Discard Reactions

最終的には、捨て牌に対するあがり判定を持つ。

MVPで後回しにする場合でも、状態設計では以下を考慮する。

- lastDiscard
- discard owner
- reaction window
- canWinFromDiscard
- pass reaction

## CPU

MVPのCPUは賢くなくてよい。

優先事項:

1. 合法手を必ず選ぶ
2. 進行不能にならない
3. 3〜4人戦が成立する
4. 後から思考改善できる構造にする

CPUも同じルールで動く。CPU専用の簡略ルールを作らない。

## Locked Assumptions

以下は固定。

- 3〜4人用
- 2人戦なし
- 通常手牌8枚
- 引いた瞬間9枚
- あがり形は3枚セット×3組
- 共通山
- 共通役表
- 役・得点はデッキ定義
- 画像はルールに影響しない

## Still Need User Decision

以下は、実装前にユーザーと決める。

- 山の総枚数の推奨値
- 牌1種類あたりの標準枚数
- 3人戦/4人戦で同じ牌数にするか
- 捨て牌あがりの優先順位
- 複数人が同時に捨て牌であがれる場合の扱い
- 複数役成立時に合計するか最大役にするか

AIはここを勝手に決めない。仮置きする場合は `TODO(user decision)` と明記する。
